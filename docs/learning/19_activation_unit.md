# 1. Introduction

The Matrix Engine produces the result of matrix multiplication.

However,

most neural networks do **not** stop after matrix multiplication.

Instead,

the output is passed through an **activation function**.

The activation function introduces non-linearity into the neural network, allowing it to learn complex relationships that cannot be represented using only linear operations.

The hardware responsible for performing these activation functions is called the **Activation Unit**.

Within this project,

the first activation function implemented is **ReLU (Rectified Linear Unit)** because of its simplicity, efficiency, and widespread adoption in modern AI workloads.

---

# 2. Why Activation Functions are Needed

Consider a neural network without activation functions.

Every layer would perform only:

```text
Output = Input × Weight
```

Even if hundreds of layers were stacked together,

the overall computation would still represent a single linear transformation.

Such a network cannot model complex patterns.

Activation functions solve this problem by introducing **non-linearity**.

This enables neural networks to approximate highly complex functions used in:

- image recognition,
- language models,
- speech processing,
- recommendation systems,
- robotics,
- autonomous vehicles.

Without activation functions,

deep learning would not be practical.

---

# 3. What is an Activation Unit?

An Activation Unit is specialized hardware that applies an activation function to every element of an input tensor or matrix.

Conceptually,

```text
Matrix Engine Output

↓

Activation Unit

↓

Activated Output
```

Unlike the Matrix Engine,

the Activation Unit performs relatively simple arithmetic or comparison operations.

Its focus is:

- applying activation functions,
- preserving throughput,
- minimizing latency,
- operating on streaming data.

---

# 4. Activation Unit Position in the Accelerator

The Activation Unit immediately follows the Matrix Engine.

```text
CPU

↓

MMIO

↓

Descriptor Fetch Unit

↓

Scheduler

↓

DMA Engine

↓

Matrix Engine

↓

Activation Unit

↓

Output Buffer

↓

DMA Write-back
```

This ordering allows matrix multiplication results to be processed before they are written back to memory.

# 7. Internal Architecture

A modular Activation Unit may consist of:

```text
Activation Unit
│
├── Controller FSM
├── Input Buffer
├── Comparator
├── Arithmetic Unit
├── Output Buffer
├── Configuration Register
└── Status Generator
```

Each block performs a dedicated function.

This modularity simplifies RTL implementation and verification.

---

# 8. Supported Activation Functions

Although many activation functions exist,

an accelerator often implements only those required by its target workloads.

Common hardware-supported activations include:

- ReLU
- Leaky ReLU
- Sigmoid
- Tanh
- Hard-Swish
- GELU

Some functions require only simple comparisons.

Others require multiplication, division, or approximation hardware.

Consequently,

hardware cost varies considerably between activation functions.

---

# 9. ReLU Operation

The Rectified Linear Unit (ReLU) is defined mathematically as:

```text
ReLU(x) = max(0, x)
```

The operation is extremely simple.

If the input is positive,

the output equals the input.

If the input is negative,

the output becomes zero.

Examples:

| Input | Output |
|--------|--------|
| 7 | 7 |
| 2 | 2 |
| 0 | 0 |
| -3 | 0 |
| -15 | 0 |

Because only a comparison is required,

ReLU is exceptionally efficient in digital hardware.

---

# 10. Hardware Implementation of ReLU

A hardware implementation of ReLU requires only:

- Sign detection
- Comparator
- Multiplexer

Conceptually,

```text
Input

↓

Sign Bit

↓

Positive?

↓

YES → Output = Input

NO → Output = 0
```

No multiplication,

division,

or lookup tables are required.

This simplicity makes ReLU one of the fastest activation functions for hardware implementation.

---

# 11. Leaky ReLU

Standard ReLU forces all negative values to zero.

Leaky ReLU instead scales negative values by a small constant.

Conceptually,

```text
Positive Input

↓

Output = Input

Negative Input

↓

Output = α × Input
```

where **α** is typically a small positive constant.

Compared with standard ReLU,

Leaky ReLU requires:

- Comparator
- Multiplier
- Constant register

The additional multiplier increases hardware complexity slightly but can improve neural network training in some applications.

---

# 12. Other Activation Functions

More advanced neural networks use activation functions such as:

### Sigmoid

Produces outputs between 0 and 1.

Widely used in binary classification.

---

### Tanh

Produces outputs between -1 and 1.

Historically popular in recurrent neural networks.

---

### GELU

Frequently used in transformer architectures.

Provides smoother activation than ReLU.

---

Unlike ReLU,

these functions cannot usually be implemented using simple comparisons alone.

Hardware implementations often rely on:

- lookup tables,
- polynomial approximations,
- piecewise-linear approximations,
- CORDIC algorithms.

These techniques trade hardware area for computational accuracy.

---

# 13. Streaming Operation

The Activation Unit is designed to operate on streaming data.

Conceptually,

```text
Matrix Result

↓

Activation Unit

↓

Output Buffer

↓

Next Value

↓

Repeat
```

Instead of waiting for an entire matrix,

each element may be processed as soon as it becomes available.

Streaming minimizes latency and maximizes pipeline utilization.

---

# 14. Pipeline Integration

The Activation Unit fits naturally into the accelerator pipeline.

```text
DMA

↓

Matrix Engine

↓

Activation Unit

↓

Output Buffer

↓

DMA Write-back
```

Because every stage operates concurrently,

multiple tensors may be processed simultaneously in different pipeline stages.

This overlap significantly improves overall accelerator throughput.

# 15. Design Philosophy

Several design principles guided the Activation Unit architecture.

### Modular Design

Each functional block performs one clearly defined task.

---

### Streaming Processing

Data should flow continuously whenever possible.

---

### Scalability

Additional activation functions can be incorporated without redesigning the entire module.

---

### Controller/Datapath Separation

The controller sequences execution.

The datapath performs arithmetic and comparisons.

---

### Verification-Friendly RTL

The architecture is intentionally structured to simplify simulation, assertions, and future formal verification.

# 16. Controller State Machine

Like every major hardware block in the accelerator, the Activation Unit is controlled by a Finite State Machine (FSM).

A simple implementation consists of the following states:

```text
IDLE

↓

LOAD_DATA

↓

ACTIVATE

↓

STORE_OUTPUT

↓

DONE

↓

IDLE
```

Each state performs one clearly defined responsibility.

This deterministic structure simplifies debugging and verification.

---

## IDLE

The Activation Unit waits for a Start signal from the Scheduler.

During this state:

- Busy = 0
- Done = 0
- Output remains unchanged

No activation operations are performed.

---

## LOAD_DATA

Input values from the Matrix Engine or input buffer are loaded into internal registers.

Typical actions include:

- Read input value
- Latch activation type
- Initialize processing counters

No arithmetic occurs during this state.

---

## ACTIVATE

This is the computational state.

Each input value passes through the selected activation function.

Examples:

- ReLU
- Leaky ReLU
- Sigmoid (future)
- Tanh (future)

Busy remains asserted throughout processing.

---

## STORE_OUTPUT

Activated values are written into the output buffer.

If streaming mode is enabled,

results may simultaneously be forwarded to the DMA write-back engine.

---

## DONE

The controller asserts Done.

Busy is cleared.

The Scheduler is notified that activation processing has completed.

The FSM then returns to IDLE.

---

# 17. Controller Responsibilities

The controller coordinates the complete activation process.

Responsibilities include:

- Accept Start signal
- Select activation type
- Control datapath timing
- Enable arithmetic units
- Detect completion
- Generate Busy
- Generate Done
- Handle reset

The controller does **not** modify activation values itself.

Instead, it controls when the datapath performs computation.

---

# 18. Datapath Responsibilities

The datapath performs all numerical operations.

Typical datapath blocks include:

```text
Input Buffer

↓

Comparator

↓

Arithmetic Unit

↓

Output Buffer
```

Depending on the selected activation function,

the datapath performs:

- Comparisons
- Multiplication
- Addition
- Lookup Table Access
- Approximation Logic

The datapath operates only when enabled by the controller.

---

# 19. Comparator

For ReLU,

the comparator determines whether the input is positive or negative.

Conceptually,

```text
Input

↓

Compare With Zero

↓

Positive?

↓

YES → Pass Input

NO → Output Zero
```

Because comparison is significantly simpler than multiplication,

ReLU has extremely low hardware cost.

---

# 20. Arithmetic Unit

Some activation functions require arithmetic operations.

Examples include:

Leaky ReLU:

```text
Output = α × Input
```

Hard-Swish:

```text
Output = x × f(x)
```

Future implementations may also require:

- fixed-point multiplication,
- floating-point multiplication,
- adders,
- shifters,
- approximation hardware.

The arithmetic unit is therefore designed to be modular and extensible.

---

# 21. Output Buffer

Activated values are stored in the output buffer before write-back.

Benefits include:

- Decoupling compute timing from DMA timing
- Preventing stalls
- Supporting burst memory writes
- Synchronizing downstream transfers

Only after buffering are results returned to memory.

---

# 22. RTL Implementation

The Activation Unit is implemented using a modular SystemVerilog architecture.

Logical organization:

```text
Activation Unit
│
├── Controller FSM
├── Configuration Register
├── Input Buffer
├── Comparator
├── Arithmetic Unit
├── Output Buffer
├── Status Generator
└── Error Detector
```

The implementation follows the same controller/datapath partition used throughout the accelerator.

Advantages include:

- Easier maintenance
- Cleaner RTL
- Better scalability
- Simplified verification
- Improved synthesis readability

---

# 23. Verification Strategy

Verification proceeds incrementally.

---

## Stage 1

Compilation

Verify:

- RTL compiles successfully.
- Packages compile.
- Testbench compiles.

---

## Stage 2

Reset Verification

Verify:

- FSM enters IDLE.
- Busy clears.
- Done clears.
- Internal registers reset.

---

## Stage 3

ReLU Verification

Verify:

Positive inputs remain unchanged.

Negative inputs become zero.

Zero remains zero.

---

## Stage 4

Streaming Verification

Verify:

- Continuous data accepted.
- No dropped values.
- Correct ordering maintained.

---

## Stage 5

Pipeline Verification

Verify:

- Scheduler starts Activation Unit.
- Matrix Engine output correctly received.
- Output buffer contains expected values.

---

## Stage 6

Future Function Verification

As new activation functions are added,

verify:

- Correct arithmetic
- Correct approximations
- Numerical accuracy within acceptable error bounds

---

# 24. Assertions

Typical SystemVerilog Assertions include:

### Reset

Activation Unit shall always enter IDLE after reset.

---

### Busy Protocol

Busy shall remain asserted while activation processing is active.

---

### Done Protocol

Done shall only assert after all input values have been processed.

---

### Function Selection

Only supported activation functions may be executed.

---

### Output Stability

Output buffer contents shall remain stable until acknowledged by the downstream module.

---

### FSM

Illegal state transitions shall never occur.

---

Assertions provide continuous protocol checking during simulation and regression testing.

# 25. Performance Optimization

Several techniques improve activation throughput.

### Streaming Processing

Process values immediately as they arrive.

---

### Pipeline Execution

Overlap activation with DMA and Matrix Engine execution.

---

### Parallel Comparators

Evaluate multiple tensor elements simultaneously.

---

### Vector Processing

Apply activation to multiple values per clock cycle.

---

### Approximation Hardware

Implement complex functions using lookup tables or piecewise-linear approximations.

These optimizations increase throughput while minimizing additional hardware cost.

# 27. Industry Perspective

Activation Units are standard components in modern AI accelerators.

Examples include:

- Google TPU
- NVIDIA Tensor Core pipelines
- Intel AI accelerators
- Qualcomm Hexagon processors
- Edge AI NPUs

Although implementations vary,

their shared objectives are:

- low latency,
- high throughput,
- efficient streaming,
- minimal hardware overhead.

Simple activations such as ReLU are typically implemented directly in hardware, while more complex functions often use approximation techniques to balance accuracy and silicon cost.

---

# 28. Common Design Mistakes

Common implementation errors include:

- Incorrect sign detection.
- Mishandling zero inputs.
- Controller asserting Done too early.
- Mixing controller and datapath logic.
- Failing to reset internal buffers.
- Unsupported activation types not generating errors.
- Pipeline stalls due to poor synchronization.
- Inadequate verification of approximation functions.

Avoiding these mistakes improves both correctness and maintainability.
