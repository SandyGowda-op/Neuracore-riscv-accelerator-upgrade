# 1. Introduction

Artificial Intelligence workloads are dominated by one operation more than any other:

**Matrix Multiplication.**

Whether performing:

- image classification,
- object detection,
- speech recognition,
- recommendation systems,
- transformer inference,
- or large language model computation,

the overwhelming majority of arithmetic operations are matrix multiplications.

For this reason, modern AI accelerators dedicate specialized hardware to perform matrix multiplication efficiently.

This hardware is commonly known as the **Matrix Engine**.

In this project, the Matrix Engine is implemented using a **Systolic Array**, one of the most widely adopted architectures for high-throughput matrix multiplication.

---

# 2. Why Matrix Multiplication Matters

Consider a fully connected neural network layer.

Its mathematical operation is:

```text
Output = Input × Weight
```

For even modest neural networks:

- thousands of rows,
- thousands of columns,
- millions of multiply-accumulate operations

must be executed.

A traditional CPU executes these operations sequentially.

Although modern CPUs contain SIMD instructions, they are still optimized for general-purpose workloads.

A dedicated Matrix Engine exploits massive parallelism, allowing many multiply-accumulate operations to execute simultaneously.

This dramatically improves throughput and energy efficiency.

---

# 3. What is a Matrix Engine?

A Matrix Engine is specialized digital hardware designed to execute matrix operations efficiently.

Its primary responsibilities include:

- matrix multiplication,
- accumulation,
- tensor computation,
- vector multiplication,
- convolution primitives.

Unlike a CPU, which executes many different instruction types, the Matrix Engine focuses on a narrow set of arithmetic operations and optimizes them aggressively.

Conceptually,

```text
Input Matrix

↓

Matrix Engine

↓

Output Matrix
```

The Matrix Engine does not fetch descriptors or move memory.

Those responsibilities belong to the Scheduler and DMA Engine.

---

# 4. Why Systolic Arrays?

Several hardware architectures exist for implementing matrix multiplication.

Examples include:

- SIMD Arrays
- Vector Processors
- GPUs
- Systolic Arrays

Among these, Systolic Arrays provide an excellent balance between:

- throughput,
- silicon area,
- power efficiency,
- data reuse.

Instead of repeatedly reading operands from memory, neighboring Processing Elements exchange data locally.

This significantly reduces memory bandwidth requirements.

As a result, systolic arrays are widely used in AI accelerators.

---

# 5. History of the Systolic Array

The concept of the systolic array was introduced by **H. T. Kung** in the early 1980s.

The idea was inspired by the rhythmic pumping action of the human heart.

Just as blood flows rhythmically through the body,

data flows rhythmically through a systolic array.

Each clock cycle,

every Processing Element performs a small computation and forwards data to neighboring elements.

This regular communication pattern enables:

- high throughput,
- deterministic timing,
- scalable hardware.

Today, systolic arrays form the computational core of many commercial AI accelerators.

# 6. Matrix Engine Position in the Accelerator

The Matrix Engine occupies the computational center of the accelerator.

```text
CPU

↓

MMIO

↓

Descriptor Fetch Unit

↓

Scheduler

↓

DMA Engine

↓

Matrix Engine

↓

Activation Unit

↓

Output Memory
```

The Scheduler determines **when** computation begins.

The DMA Engine supplies input data.

The Matrix Engine performs the computation.

# 9. Internal Architecture

A Matrix Engine consists of multiple interacting components.

```text
Matrix Engine
│
├── Controller FSM
├── Input Buffers
├── Weight Buffers
├── Processing Element Array
├── Accumulator Registers
├── Output Buffer
└── Status Generator
```

Each block performs one specialized function.

The modular architecture simplifies verification and future scaling.

---

# 10. Processing Elements (PEs)

The fundamental computational unit of a systolic array is the **Processing Element (PE).**

Each PE performs a simple operation:

```text
Multiply

↓

Accumulate

↓

Forward Data
```

Mathematically,

```text
Accumulator = Accumulator + (A × B)
```

Every clock cycle,

each PE receives operands from neighboring PEs,

computes one multiply-accumulate (MAC),

updates its accumulator,

and forwards data to adjacent PEs.

Because all PEs operate simultaneously,

overall throughput increases dramatically.

---

# 11. Processing Element Architecture

A typical PE contains:

```text
Processing Element
│
├── Input Register A
├── Input Register B
├── Multiplier
├── Accumulator
├── Output Register A
├── Output Register B
└── Control Logic
```

The PE is intentionally simple.

Complexity is achieved through the cooperation of many PEs operating together rather than by making each PE individually sophisticated.

---

# 12. Dataflow Inside the Systolic Array

Data moves through the array in a highly structured manner.

```text
Matrix A

→ → → →

Processing Elements

← ← ← ←

Matrix B
```

Each Processing Element exchanges operands only with its immediate neighbors.

No global routing network is required.

This local communication significantly reduces routing complexity and power consumption.

---

# 13. Matrix Multiplication Flow

A matrix multiplication proceeds through several stages.

```text
DMA Loads Matrix A

↓

DMA Loads Matrix B

↓

Scheduler Starts Matrix Engine

↓

Operands Enter Processing Elements

↓

Multiply-Accumulate Operations

↓

Partial Sums Propagate

↓

Final Results Stored

↓

Done
```

The Matrix Engine focuses solely on arithmetic.

Memory transfers remain the responsibility of the DMA Engine.

---

# 14. Data Reuse

One of the greatest strengths of the systolic array is data reuse.

Instead of repeatedly fetching operands from memory,

each Processing Element forwards operands to neighboring elements.

Example:

```text
PE1 → PE2 → PE3 → PE4
```

A single operand participates in multiple computations while remaining inside the array.

Benefits include:

- Reduced memory bandwidth
- Lower energy consumption
- Higher throughput
- Improved hardware utilization

This is one of the primary reasons systolic arrays outperform naïve matrix multiplication architectures.

---

# 15. Parallelism

Unlike sequential processors,

all Processing Elements operate simultaneously.

Example:

```text
Clock Cycle 1

PE1
PE2
PE3
PE4

All Compute Together
```

As the array size increases,

the number of concurrent multiply-accumulate operations also increases.

This fine-grained parallelism enables AI accelerators to sustain very high computational throughput.

---
# 16. Array Timing

Unlike a conventional processor, where one instruction is completed before the next begins, a systolic array behaves like a pipeline.

After the array is filled with data, every clock cycle produces new partial results.

Conceptually,

```text
Cycle 1

A enters PE(0,0)

↓

Cycle 2

A moves to PE(0,1)

New A enters PE(0,0)

↓

Cycle 3

Data continues propagating

↓

...

↓

Steady State

One MAC operation occurs inside every PE each clock cycle.
```

This pipeline behavior allows extremely high throughput.

Although initial latency exists while the array fills, the steady-state performance is exceptionally high.

---

# 17. Pipeline Fill and Drain

Every systolic array experiences two phases.

## Fill Phase

Initially,

only a few Processing Elements contain valid data.

Example:

```text
Cycle 1

X . . .

. . . .

. . . .

. . . .
```

---

## Steady-State Phase

Eventually,

all Processing Elements become active.

```text
X X X X

X X X X

X X X X

X X X X
```

Maximum computational throughput is achieved during this phase.

---

## Drain Phase

After new operands stop entering,

partial sums continue propagating until every Processing Element finishes computation.

```text
Cycle N

Results exit array

↓

Done
```

Understanding fill and drain latency is essential when estimating accelerator performance.

---

# 18. Processing Element Communication

Each Processing Element communicates only with its immediate neighbors.

For a PE located at position *(i,j)*,

typical communication is:

```text
        Matrix A →

PE(i,j)

↓

Matrix B
```

Outputs are forwarded as follows:

- Matrix A moves horizontally.
- Matrix B moves vertically.
- Partial sums remain local until completion.

Because communication is entirely local,

routing complexity grows much more slowly than in fully connected architectures.

---

# 19. Controller FSM

Although the Processing Elements perform arithmetic,

the Matrix Engine still requires a controller.

A simple controller FSM consists of:

```text
IDLE

↓

LOAD_INPUTS

↓

COMPUTE

↓

STORE_RESULTS

↓

DONE

↓

IDLE
```

Each state coordinates one stage of execution.

---

## IDLE

Wait for the Scheduler.

Outputs:

- Busy = 0
- Done = 0

---

## LOAD_INPUTS

Receive operands from the DMA Engine.

Initialize internal counters.

---

## COMPUTE

Enable all Processing Elements.

Matrix multiplication proceeds over multiple clock cycles.

Busy remains asserted.

---

## STORE_RESULTS

Transfer accumulated results into the output buffer.

Prepare results for DMA write-back.

---

## DONE

Assert Done.

Clear Busy.

Notify the Scheduler that computation has completed.

Return to IDLE.

---

# 20. Controller Responsibilities

The controller performs the following tasks:

- Receive Start signal.
- Initialize Processing Elements.
- Control execution timing.
- Track computation progress.
- Detect completion.
- Generate Done.
- Handle reset.

Importantly,

the controller **never performs arithmetic**.

It only coordinates execution.

---

# 21. Datapath Responsibilities

The datapath contains the computational hardware.

Typical datapath blocks include:

```text
Input Buffers

↓

PE Array

↓

Accumulator Registers

↓

Output Buffer
```

The datapath executes every multiply-accumulate operation.

The controller simply determines **when** each stage operates.

---

# 22. Accumulator Registers

Each Processing Element contains an accumulator register.

Instead of producing an output immediately after multiplication,

the PE repeatedly accumulates partial sums.

Example:

```text
Accumulator

↓

Accumulator + (A × B)

↓

Accumulator + (A × B)

↓

...

↓

Final Result
```

Accumulation significantly reduces memory traffic because intermediate values remain inside the array.

---

# 23. Output Buffer

After computation completes,

results are written into an output buffer.

The output buffer serves several purposes:

- stores completed matrix values,
- isolates compute timing from DMA timing,
- prevents pipeline stalls,
- supports burst memory writes.

Only after buffering are results transferred back to memory.

---

# 24. RTL Implementation

The Matrix Engine is implemented using a modular SystemVerilog architecture.

Logical organization:

```text
Matrix Engine
│
├── Controller FSM
├── Input Buffers
├── PE Array
├── Accumulator Registers
├── Output Buffer
├── Status Generator
└── Configuration Registers
```

The design follows a clear controller/datapath partition.

Benefits include:

- modular RTL,
- easier synthesis,
- improved readability,
- scalable architecture,
- simplified verification.

Verification proceeds incrementally.

## Stage 1

Compilation

- RTL compiles.
- Packages compile.
- Testbench compiles.

---

## Stage 2

Reset Verification

Verify:

- Controller enters IDLE.
- Busy clears.
- Done clears.
- Accumulators reset.

---

## Stage 3

Processing Element Verification

Verify:

- Correct multiplication.
- Correct accumulation.
- Correct forwarding.

---

## Stage 4

Array Verification

Verify:

- Correct data propagation.
- Correct synchronization.
- Expected output matrix.

---

## Stage 5

End-to-End Verification

Verify:

- DMA supplies correct operands.
- Scheduler starts computation.
- Matrix Engine produces expected results.
- Results returned correctly.

# 26. Assertions for the Matrix Engine

Typical SystemVerilog Assertions include:

### Reset

Controller shall enter IDLE after reset.

---

### Busy

Busy shall remain asserted during computation.

---

### Done

Done shall only assert after every Processing Element has completed.

---

### Processing Element Enable

PEs shall only compute during the COMPUTE state.

---

### FSM

Illegal state transitions shall never occur.

---

### Output Stability

Output buffer contents shall remain stable until acknowledged.

---

Assertions greatly simplify debugging and regression testing.

# 27. Performance Optimization Techniques

Several techniques improve systolic array performance.

### Loop Tiling

Break large matrices into smaller blocks.

---

### Double Buffering

Load new operands while current computation executes.

---

### Data Reuse

Reuse operands inside the array rather than rereading memory.

---

### Burst DMA

Supply operands efficiently.

---

### Pipeline Scheduling

Overlap:

- DMA
- Computation
- Output transfer

These optimizations maximize accelerator utilization.

# 29. Industry Perspective

Systolic arrays form the computational backbone of many commercial AI accelerators.

Examples include:

- Google TPU Matrix Units
- AI inference NPUs
- Edge AI accelerators
- FPGA-based machine learning accelerators
- Custom ASIC tensor processors

Although implementations differ in precision, interconnect, and scheduling, they all rely on the same fundamental principles:

- local data movement,
- massive parallelism,
- high data reuse,
- pipelined execution.

Mastering systolic array architecture therefore provides a strong foundation for understanding industrial AI hardware.

# 30. Common Design Mistakes

Typical implementation errors include:

- Incorrect PE interconnections.
- Misaligned operand timing.
- Failure to reset accumulators.
- Controller issuing Done too early.
- Buffer overflow due to insufficient synchronization.
- Incorrect handling of pipeline fill and drain.
- Ignoring memory bandwidth limitations.
- Mixing controller and datapath responsibilities.

Avoiding these issues improves correctness and simplifies verification.
