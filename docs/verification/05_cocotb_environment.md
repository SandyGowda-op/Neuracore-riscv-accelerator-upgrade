# 1. Purpose

This document defines the Cocotb-based verification environment used to verify the AI Accelerator RTL.

The environment provides:

- Automated test execution
- Python-based stimulus generation
- Automated checking
- Regression support
- Integration with the Golden Reference Model
- Functional verification independent of simulator vendor

The goal is to create a reusable and scalable verification framework.

---

# 2. Why Cocotb?

Cocotb (Coroutine-based Cosimulation TestBench) allows RTL to be verified using Python instead of writing traditional HDL-only testbenches.

Advantages include:

- Faster test development
- Readable verification code
- Easy integration with NumPy
- Direct use of Python libraries
- Excellent support for random testing
- Easier maintenance
- Simulator independence

For matrix-intensive accelerators, Python provides a natural environment for generating and verifying numerical results.

# 6. Testbench Components

Examples:

- MMIO writes

- DMA requests
- Reset sequences

## Monitor

Observes DUT activity.

Examples:

- DMA transfers

# 8. Clock and Reset Generation

Each testcase initializes a stable clock and reset.

Clock requirements:

- Fixed period
- Continuous toggling
- Stable before stimulus

Reset requirements:

- Assert during initialization
- Hold for required cycles
- Release cleanly
- Verify DUT returns to idle state

All testcases should begin from a known reset state.

---

# 9. Driver Architecture

Drivers are responsible for stimulating DUT interfaces.

Typical driver operations include:

- Writing MMIO registers
- Loading descriptors
- Initializing memory
- Starting accelerator execution
- Waiting for completion

Drivers should never verify outputs; their responsibility is limited to generating valid stimulus.

---

# 10. Monitor Architecture

Monitors observe DUT behavior without modifying it.

Typical monitored interfaces include:

- MMIO transactions
- DMA activity
- Scratchpad accesses
- Matrix engine outputs
- Activation unit outputs
- Status register updates

Captured transactions are forwarded to the scoreboard.

---

# 11. Scoreboard Integration

The scoreboard receives:

- Expected results from the Reference Model
- Actual results from monitors

Comparison process:

```text
Monitor Output

↓

Scoreboard

↑

Reference Model

↓

PASS / FAIL
```

The scoreboard produces detailed mismatch reports whenever discrepancies are detected.

---

# 12. Reference Model Integration

The Cocotb environment invokes the Python Reference Model before comparing DUT outputs.

Example workflow:

1. Generate input matrices.
2. Execute the software model.
3. Store expected outputs.
4. Execute RTL.
5. Compare results.

The Reference Model remains independent of the RTL implementation.

---

# 13. Logging Strategy

Each simulation produces structured logs.

Typical information includes:

```text
Simulation Started

Reset Applied

Descriptor Loaded

DMA Started

Matrix Engine Started

Activation Complete

Write-back Complete

Scoreboard PASS

Simulation Finished
```

On failure, logs should include:

- Simulation time
- Testcase name
- Expected value
- Actual value
- Module involved
- Descriptor number (if applicable)

This facilitates rapid debugging.

---

# 14. Writing Testcases

Each testcase should follow a consistent structure.

Typical sequence:

1. Initialize DUT
2. Start clock
3. Apply reset
4. Configure accelerator
5. Load input data
6. Execute operation
7. Wait for completion
8. Collect outputs
9. Compare with reference model
10. Report PASS or FAIL

Testcases should verify one primary objective whenever possible.

---

# 15. Running Simulations

A typical simulation workflow consists of:

1. Compile RTL sources.
2. Launch the simulator.
3. Execute the selected Cocotb testcase.
4. Generate waveforms (optional).
5. Produce simulation logs.
6. Update regression results.

Individual tests should also be runnable as part of a larger automated regression suite.

---

# 16. Debugging Workflow

When a failure occurs, the recommended debugging sequence is:

```text
Simulation Failure

↓

Review Log Messages

↓

Identify First Failure

↓

Check Scoreboard Output

↓

Inspect Waveforms

↓

Compare with Reference Model

↓

Locate RTL Issue

↓

Fix RTL

↓

Re-run Test

↓

Run Regression
```

Debugging should always begin with the earliest reported error to avoid chasing secondary failures.

# 17. Best Practices

The following guidelines improve maintainability and reliability:

- Keep testcases independent.
- Avoid duplicated verification code.
- Reuse drivers and monitors.
- Maintain deterministic tests where possible.
- Use randomization with reproducible seeds.
- Compare against the Reference Model rather than hard-coded values.
- Ensure every bug fix includes a regression testcase.
- Keep utility functions generic and reusable.
- Document assumptions within each testcase.

Following these practices simplifies long-term maintenance as the design evolves.
