# 1. Purpose

The scoreboard is responsible for determining whether the RTL implementation produces the correct outputs.

Unlike a monitor, which only observes signals, the scoreboard performs intelligent comparisons between:

- Expected results
- Actual RTL outputs

The scoreboard serves as the final decision-making component in the verification environment.

---

# 2. Scope

The scoreboard verifies:

- Matrix multiplication
- ReLU activation
- DMA transfers
- Scratchpad contents
- MMIO transactions
- Descriptor execution
- Accelerator completion status
- End-to-end workload correctness

---

# 3. What is a Scoreboard?

A scoreboard is an automated checker.

It receives:

- Expected outputs generated by a reference model
- Actual outputs generated by the DUT

It compares both datasets and reports:

- PASS
- FAIL
- Detailed mismatch information

Without a scoreboard, verification would require manually inspecting waveforms, making regression testing impractical.

---

# 4. Verification Architecture

The scoreboard is positioned between the DUT outputs and the reference model.

```text
                Testbench
                     │
          Apply Stimulus
                     │
        ┌────────────┴────────────┐
        │                         │
        ▼                         ▼
      DUT                  Reference Model
        │                         │
        └────────────┬────────────┘
                     ▼
               Scoreboard
                     │
          PASS / FAIL Report
```

The scoreboard never generates stimulus; it only evaluates correctness.

---

# 5. Inputs to the Scoreboard

The scoreboard receives two independent datasets.

## Expected Data

Generated by the Python golden reference model.

Examples:

- Expected matrix output
- Expected ReLU output
- Expected DMA destination memory
- Expected status register values

---

## Actual Data

Collected directly from the RTL.

Examples:

- Matrix engine outputs
- Scratchpad contents
- DMA write-back memory
- MMIO status registers
- Completion signals

---

# 6. Expected Data Generation

Expected outputs are generated using software models.

For example:

1. Load input matrices.
2. Execute matrix multiplication using NumPy.
3. Apply ReLU in software.
4. Generate expected output matrix.
5. Store results for comparison.

The reference model is considered the source of truth.

---

# 7. Actual DUT Data Collection

The scoreboard receives DUT outputs through monitors.

Monitors observe interfaces such as:

- DMA transactions
- Scratchpad writes
- Matrix engine outputs
- MMIO register accesses
- Accelerator completion

The scoreboard does not directly probe internal RTL signals unless specifically configured.

---

# 8. Comparison Strategy

Each observed transaction is compared against the expected result.

General comparison procedure:

```text
Expected Output

↓

Actual Output

↓

Element-by-Element Comparison

↓

PASS / FAIL
```

Every mismatch is reported with sufficient detail for debugging.

---

# 9. Supported Comparisons

The scoreboard supports multiple comparison types.

## Exact Value Comparison

Used for:

- Registers
- Addresses
- Control signals
- Descriptor fields

Example:

Expected:

```text
Busy = 1
```

Actual:

```text
Busy = 1
```

PASS

---

## Array Comparison

Used for:

- Matrix outputs
- Scratchpad memory
- DMA buffers

Each element is compared individually.

---

## Transaction Comparison

Used for:

- DMA requests
- MMIO writes
- MMIO reads

Each transaction is checked for:

- Address
- Data
- Timing order
- Transaction validity

---

# 10. Error Reporting

Every mismatch shall include:

- Test name
- Simulation time
- Expected value
- Actual value
- Interface
- Descriptor number
- Matrix coordinates (if applicable)

Example:

```text
ERROR

Descriptor : 5

Matrix Element : [2][3]

Expected : 18

Actual : 17
```

This information significantly reduces debugging effort.

---

# 11. Scoreboard Workflow

Standard workflow:

```text
Start Test

↓

Receive Expected Data

↓

Receive DUT Output

↓

Compare

↓

Generate Report

↓

Store Statistics

↓

PASS / FAIL
```

This process repeats until simulation completes.

---

# 12. Handling Timing Differences

The DUT may produce outputs later than the reference model.

Therefore, comparisons are synchronized using:

- Completion signals
- Valid flags
- Done signals
- Transaction queues

The scoreboard compares outputs only after the DUT indicates that data is valid.

This prevents false failures caused by latency differences.

---

# 13. Descriptor-Level Verification

Each descriptor execution is verified independently.

Checks include:

- Descriptor fetched correctly
- Correct DMA source
- Correct DMA destination
- Matrix computation completed
- Activation applied
- Results written back
- Busy cleared
- Done asserted

This allows failures to be isolated to a specific descriptor.

---

# 14. Matrix Verification

Matrix verification is the primary responsibility of the scoreboard.

Procedure:

1. Load input matrices.
2. Execute NumPy multiplication.
3. Capture DUT output matrix.
4. Compare every element.

Example:

Expected:

```text
[12 18]
[20 31]
```

Actual:

```text
[12 18]
[20 31]
```

PASS

Any mismatch identifies the exact row and column affected.

---

# 15. Activation Verification

The scoreboard verifies activation functions separately.

For ReLU:

Input:

```text
[-3 5 -1 9]
```

Expected Output:

```text
[0 5 0 9]
```

The RTL output must match exactly.

---

# 16. DMA Verification

DMA verification checks:

- Source address
- Destination address
- Transfer length
- Data integrity
- Burst completion

Expected memory after transfer is compared with actual memory contents.

---

# 17. MMIO Verification

MMIO verification includes:

- Register writes
- Register reads
- Busy status
- Done status
- Error status

Every register access is checked for correctness.

---

# 18. Pass/Fail Rules

A test is considered PASS only if:

- Every expected transaction matches.
- Every matrix element matches.
- Every DMA transfer matches.
- Every activation result matches.
- No unexpected transactions occur.
- No expected transaction is missing.

A single mismatch results in test failure.

---

# 19. Logging Strategy

The scoreboard generates detailed logs.

Typical summary:

```text
====================================

Descriptors Executed : 24

Matrices Verified    : 24

DMA Transfers        : 48

MMIO Transactions    : 16

Errors               : 0

STATUS : PASS

====================================
```

Logs should be human-readable and suitable for automated regression systems.

---

# 20. Future Extensions

The scoreboard architecture is designed to support future accelerator enhancements.

Potential extensions include:

- Additional activation functions (Sigmoid, Tanh, GELU)
- Quantized arithmetic (INT8, BF16, FP16)
- Sparse matrix operations
- Multiple matrix engines
- Multi-channel DMA
- Descriptor dependency checking
- Performance metric collection
- Latency and throughput analysis

By maintaining a modular scoreboard architecture, new features can be verified with minimal modifications to the existing verification infrastructure.
