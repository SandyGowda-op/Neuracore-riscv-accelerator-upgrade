# 1. Purpose

The Reference Model is a software implementation of the accelerator's intended functionality.

Its purpose is to produce mathematically correct outputs for a given set of inputs so that the RTL implementation can be verified against a trusted source.

Rather than checking RTL signals manually, the verification environment compares RTL results with the outputs generated by the Reference Model.

---

# 2. Scope

The Reference Model covers the functional behavior of:

- Matrix multiplication
- Activation functions
- Descriptor execution
- DMA data movement
- Scratchpad memory updates
- MMIO register behavior
- Accelerator status generation

The model focuses on functional correctness rather than hardware timing.

---

# 3. What is a Reference Model?

A Reference Model (also called a Golden Model) is an executable software description of the expected behavior of the hardware.

Unlike RTL, the model:

- ignores implementation details,
- does not simulate clock cycles,
- does not contain finite state machines,
- computes results directly using algorithms.

Its output represents the expected behavior of the design.

---

# 4. Design Philosophy

The Reference Model should satisfy the following principles:

## Correctness

The model must always generate mathematically correct outputs.

---

## Simplicity

The implementation should prioritize readability over optimization.

---

## Determinism

Given identical inputs, the model must always produce identical outputs.

---

## Independence

The model must not reuse RTL logic.

Reusing RTL algorithms defeats the purpose of independent verification.

---

## Maintainability

Each hardware feature should have a corresponding software implementation that can be updated independently.

---

# 5. Reference Model Architecture

The model consists of several independent software modules.

```text
Input Stimulus

↓

Descriptor Parser

↓

DMA Model

↓

Scratchpad Model

↓

Matrix Engine Model

↓

Activation Model

↓

Result Generator

↓

Expected Output
```

Each module mirrors the functionality—not the implementation—of its RTL counterpart.

---

# 6. Inputs

The model accepts the same logical inputs provided to the hardware.

These include:

- Input matrices
- Descriptor information
- MMIO commands
- Activation mode
- Memory addresses
- Matrix dimensions

All inputs are validated before execution.

---

# 7. Outputs

The model produces:

- Output matrix
- Activated matrix
- Scratchpad contents
- Memory write-back data
- MMIO status values
- Completion status
- Error status (if applicable)

These outputs become the expected values used by the scoreboard.

---

# 8. Matrix Multiplication Model

Matrix multiplication is implemented using standard mathematical algorithms.

Example:

Given

```text
A =

1 2
3 4
```

and

```text
B =

5 6
7 8
```

The expected output is

```text
19 22
43 50
```

For verification efficiency, the implementation may use libraries such as NumPy.

Regardless of implementation, the generated results must remain mathematically correct.

---

# 9. Activation Function Model

The activation model applies the selected activation function after matrix multiplication.

Current implementation supports:

## ReLU

Definition

```text
Output = max(0, Input)
```

Example

Input

```text
[-5 3 -2 8]
```

Output

```text
[0 3 0 8]
```

The model architecture allows additional activation functions to be added without affecting existing functionality.

---

# 10. DMA Behavioral Model

The DMA model simulates memory movement without modeling hardware timing.

Responsibilities include:

- Reading source memory
- Writing destination memory
- Address incrementing
- Burst transfers
- Boundary checking

The model assumes data transfers complete successfully unless an invalid condition is explicitly injected.

---

# 11. Descriptor Execution Model

Descriptors are interpreted sequentially.

Execution flow:

```text
Read Descriptor

↓

Decode Fields

↓

Move Input Data

↓

Perform Matrix Multiplication

↓

Apply Activation

↓

Write Output

↓

Update Status
```

The model performs these operations instantaneously from a functional perspective.

---

# 12. MMIO Behavioral Model

The MMIO model emulates software interaction with the accelerator.

Supported operations include:

- Register reads
- Register writes
- Start command
- Busy status
- Done status
- Error reporting

Illegal accesses generate predictable error responses.

---

# 13. Scratchpad Memory Model

The scratchpad model represents internal accelerator memory.

Responsibilities include:

- Operand storage
- Intermediate result storage
- Read/write operations
- Address validation

The memory model maintains a software representation of scratchpad contents throughout execution.

---

# 14. Model Validation

The Reference Model must itself be validated before being used for RTL verification.

Validation methods include:

- Manual calculation of known examples
- Comparison against trusted mathematical libraries
- Unit testing of individual functions
- Review of algorithm implementations

Only a validated model should be used as the verification reference.

---

# 15. Interaction with the Scoreboard

The scoreboard retrieves expected values directly from the Reference Model.

Verification flow:

```text
Stimulus

↓

Reference Model

↓

Expected Output

↓

Scoreboard

↓

Compare with RTL Output

↓

PASS / FAIL
```

The Reference Model never communicates directly with the DUT.

---

# 16. Synchronization Strategy

The Reference Model executes without regard to clock cycles.

To accommodate RTL latency:

- Expected outputs are stored.
- The scoreboard waits for DUT completion.
- Comparisons occur only after valid data is available.

This decouples functional correctness from implementation timing.

---

# 17. Error Handling

The Reference Model detects invalid inputs such as:

- Unsupported activation modes
- Invalid descriptors
- Illegal memory addresses
- Dimension mismatches

When errors occur, the model generates deterministic error responses that can be verified against the RTL implementation.

---

# 18. Limitations

The Reference Model intentionally omits hardware-specific behavior.

It does not model:

- Clock cycles
- Pipeline stages
- Resource contention
- Timing delays
- FSM transitions
- Signal propagation

Its purpose is functional validation, not hardware simulation.

---

# 19. Future Extensions

The architecture is designed to support future accelerator features, including:

- INT8 inference
- BF16 arithmetic
- FP16 support
- FP8 support
- Quantized operations
- Sparse matrix acceleration
- Additional activation functions
- Descriptor chaining
- Multiple DMA channels
- Multi-core accelerator configurations

Extending the Reference Model should not require changes to existing verification infrastructure.
